OpenAPI DTO Generator

Зачем

Что получаем из одного файла и в каком состоянии это сейчас

Главная идея: спецификация — единственный источник правды. Генерация запускается в CI, поэтому расхождение «контракт ↔ код» становится заметным на сборке, а не на ревью.
Честно: статусы в таблице — по результатам проверки сборкой. Подробности — слайды 15 и 24.

Почему две модели данных

IR сознательно беднее документа: в нём нет additionalProperties, readOnly, examples, uniqueItems. Для DTO и валидаторов этого достаточно. Для JSON Schema — нет, поэтому она идёт по сырому дереву (слайд 17).

Почему генераторы не пишут на диск

Каждый генератор возвращает GeneratedFile(Name, Content). Тесты сравнивают строки, ввод-вывод сосредоточен в CLI.

CLI

Что делает executor и когда включается каждый генератор

  1. Читает файл. Нет файла — код 2.
  2. Парсит YamlDocumentParser. Ошибка формата — код 3.
  3. Строит IR через IRBuilder, который вызывает RefResolver для каждой ссылки.
  4. Генерирует каждый артефакт, если он не выключен флагом --*-only.
  5. Пишет файлы в подкаталоги Dto/, Validators/, Masking/, JsonSchema/.
Маскировка включается наличием конфига, а не флагом: без --masking-config нет правил, нет инфраструктуры и нет partial-классов.

Парсинг YAML · 1/2

Зачем RepresentationModel, а не десериализация в классы

YamlStream.Load читает документ в дерево узлов, без знания о схеме OpenAPI:

  • Нужны все ключевые слова схемы, включая неизвестные x-* и будущие поля. Типизированная модель OpenAPI их отбрасывает.
  • Важен стиль скаляра: series: '4510' и series: 4510 — разные вещи для minLength и pattern.
  • JSON разбирается тем же кодом: JSON — подмножество YAML.
Ограничение: обрабатывается только первый документ (Documents[0]). Multi-document YAML с --- не поддерживается.

Парсинг YAML · 2/2

Почему тип скаляра важен для валидации

Правило идёт за строкой

minLength, pattern, format применяются к строкам. Если серия паспорта распозналась как число, правило молча пропадёт или станет неверным. Поэтому кавычки в YAML — это данные, а не оформление.

Что это значит для автора спецификации

Пишите version: '1.10', а не version: 1.10. Версии, коды и серии — всегда в кавычках.

Проверка: тесты Core.Tests покрывают quoted-скаляры и plain-числа. Тип скаляра проверяется на уровне дерева, а не конечного C#-типа.

Четыре вида ссылок и как они разрешаются

ПримерВидЧто происходит

Порядок проверки в RefParser.Parse: # → http(s):// → абсолютный путь → всё остальное как относительный путь.

JSON Pointer (RFC 6901)
// «#/components/schemas/a~1b» → сегменты:
//   components, schemas, "a/b"
// ~1 заменяется на /, затем ~0 на ~
return pointer.Split('/').Last()
    .Replace("~1", "/").Replace("~0", "~");
Документы, на которые ссылаются, кешируются по ключу, поэтому один внешний файл читается и парсится один раз на запуск.
IR · построение

Как IRBuilder строит граф SchemaNode

  1. Берёт components/schemas — каждая схема становится узлом с именем.
  2. Тип, описание, правила — type, description, minLength, pattern, format, nullable и др.
  3. enum — если есть, узел получает EnumValues и дальше не обрабатывается.
  4. array — items разбирается через inline-путь (один уровень).
  5. object — properties и required в PropertyNode.
  6. allOf / oneOf / anyOf — списки подсхем, для oneOf — discriminator.
Цикл: IRBuilder ↔ RefResolver
using (_cycleDetector.Scope(schemaName))
{
    // строим узел
}
catch (CyclicReferenceException)
    → new SchemaNode { IsLazyRef = true }
Слабое место: BuildSchemaNodeFromInlineAsync не заходит в properties и items inline-схем. Поэтому массив-свойство получает Items = null, а объект-свойство остаётся безымянным object.

DtoGenerator: что пишет в файл

  • [JsonPropertyName] хранит имя из спецификации, а C#-имя — PascalCase.
  • Необязательное свойство (не в required) получает ?, если тип не List<>.
  • description становится XML-doc.
  • allOf с именованной базой без своих свойств → наследование; остальные части добавляют свойства.
  • Enum генерируется отдельным файлом с [EnumMember(Value = …)].
Чтобы inline-enum стал отдельным типом, его нужно вынести в components/schemas.

Почему функция, а не шаблон

RuleMapper.Map(prop) возвращает IReadOnlyList<string>. Это чистая функция: таблица вход → выход, её легко тестировать.

Описание становится сообщением

WithMessage("…") берётся из description. Поэтому переносы строк в описании ломают код (CS1010) — см. слайд 24.

Нет правил для: uniqueItems, maxProperties, additionalProperties. Они есть в JSON Schema, но не в валидаторах.
Валидаторы · каркас

Каскад, условия и почему эвристика хрупкая

ValidatorGenerator — фрагмент вывода
public class SendRequestValidator : AbstractValidator<SendRequest>

    {

            .NotEmpty()
            .MinimumLength(1).WithMessage("…");

        RuleFor(x => x.Items)
            .NotNull()
            .Must(list => list == null || list.Count >= 1)

SetValidator — каскад

Если тип свойства — именованный класс, добавляется SetValidator(new XValidator()). Это работает, пока у класса есть свой валидатор.

When — условная валидация

Поля связываются с дискриминатором по совпадению подстроки в имени: passport ↔ PassportInfo. Это эвристика. Переименование схемы или поля ломает её без ошибки.

Валидаторы строятся из IR, поэтому свойство-массив получает правила по minItems, но без проверки элементов (Items не разобран).

Маскировка · замысел

Почему маскировка сделана именно так

masking-config.yaml → атрибут в DTO
masking:
  rules:
    - fields: [series, number]
      strategy: partial
      visibleStart: 2
      visibleEnd: 2
[Mask(MaskStrategy.Partial, 2, 2)]
[JsonPropertyName("series")]
public string Series { get; set; }
  • Правила в одном месте. YAML описывает, какие поля секретны. Генератор переносит это в атрибут, поэтому правило живёт рядом с полем.
  • Отдельный метод, а не глобальный логгер. ToMaskedJson() вызывает разработчик. Обычная сериализация не меняется, и не маскирует то, что нужно отправить клиенту.
  • partial-класс. {Name}.Masking.cs дополняет DTO и не перезаписывает ручной код.
  • Маскировка на границе сериализации, а не регулярками по тексту лога: правило привязано к полю, а не к значению.
Альтернативы и почему нет: regex по логу ломается на формате и пропускает значения без шаблона; ручной ToString() расходится с моделью при каждом изменении.
Маскировка · состояние

Что происходит на самом деле — проверено запуском

1. Сборка: CS0120
// MaskingJsonConverter.cs(55): GetType() в static-методе
copy.Converters[i].GetType() == GetType()
2. Регистрация: нет
// MaskingJsonOptions.Default не содержит конвертера,
// у DTO нет [JsonConverter(...)]. System.Text.Json
// не читает [Mask] сам по себе.
3. Результат после правки CS0120 (проверка в отдельном проекте)
ToMaskedJson: {"name":"Ivan","priority":2,"items":[]}
Serialize:    {"name":"Ivan","priority":2,"metadata":null,"items":[]}
Маска не применяется. name с firstChar выводится полностью. ToMaskedJson() сейчас эквивалентен обычной сериализации (кроме null, которые пропускаются).
Исправление — подключить конвертер на уровне класса или в опциях и исправить GetType(). Тесты это не ловили: они проверяют текст, а не результат.

Поиск по имени поля

FindRuleForField(name) ищет имя без учёта регистра и без пути. Правило number сработает в любом классе с полем number.

Только строки

[Mask] применяется к string. Правило на объектное или числовое поле не даёт эффекта.

Это осознанный компромисс: правила короткие и читаемые, но точность по пути и типу не гарантирована.
JSON Schema · зачем отдельный путь

Почему схема строится по сырому дереву, а не по IR

Схема запроса должна проверять то же, что написано в спецификации. IR этого не хранит:

Нужно для схемыВ IR?
additionalPropertiesнет
readOnlyнет
uniqueItems, maxProperties, patternPropertiesнет
все $ref-цепочки, включая components/requestBodiesчастично
inline-объекты внутри свойствтеряются

Цена решения

Два пути обхода документа. Конвертер ключевых слов нужно поддерживать отдельно от IR.

Выигрыш

Схема проверяет то, что реально написано. Файл самодостаточен и читается любым JSON Schema-валидатором.

JSON Schema · алгоритм

От requestBody до файла: обход и очередь

  1. Операции: по paths и методам из --json-schema-methods (по умолчанию post).
  2. requestBody: ResolveRefChainAsync разворачивает $ref до объекта, защищаясь от циклов в самих ссылках.
  3. Медиатипы: JSON и +json. Каждый — отдельный файл.
  4. Конвертация: ConvertSchemaAsync рекурсивно копирует ключевые слова и переписывает $ref.
  5. Очередь: каждый встреченный $ref ставится в Pending, пока не сконвертирован. Все записи идут в $defs.
  6. Файл: $schema + корневой объект + $defs.
RegisterDefAsync — сердце самодостаточности
if (!ctx.DefNames.TryGetValue(refKey, out var defName))
{
    defName = ctx.ReserveDefName(BuildDefBaseName(pointer, targetKey));
    ctx.DefNames[refKey] = defName;           // имя занято ДО обхода
    ctx.Pending.Enqueue(new PendingDef(defName, target, targetKey));
}
return $"#/$defs/{defName}";
Имя резервируется до конвертации. Поэтому самоссылка (Comment → replies → Comment) не уходит в бесконечный цикл: второй раз найдётся уже известное имя.
JSON Schema · $defs

$defs: одна схема на цель, имена и детерминизм

$defs — ключевое слово JSON Schema 2020-12 для именованных подсхем. На них ссылаются через $ref: "#/$defs/Name". Файл остаётся самодостаточным: он не обращается ни к каким другим файлам.

  • Ключ дедупликации — «документ + pointer», а не имя. Money из двух файлов станут Money и Money_2.
  • Имя — последний сегмент pointer'а; для ссылки на весь файл — имя файла без расширения.
  • Санитайзер оставляет a-zA-Z0-9 _ - ., остальное заменяет на _.
  • Порядок — SortedDictionary, поэтому diff в git стабилен.
sendPayload.Rq.schema.json (фрагмент)
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$ref": "#/$defs/SendRequest",
  "$defs": {
    "Item": { "type": "object", … },
    "SendRequest": {
      "properties": {
        "items": { "items": { "$ref": "#/$defs/Item" } }
      }
    }
  }
}
В корне — ссылка, а не копия схемы: $ref в OpenAPI 3.0 отменяет соседние ключи, и генератор сохраняет это правило.
JSON Schema · ключевые слова

Конвертация OpenAPI 3.0 → draft 2020-12

OpenAPI 3.0JSON Schema 2020-12Зачем

Переносится как есть: type, properties, items, allOf/oneOf/anyOf, pattern, minLength, minimum, enum, additionalProperties, uniqueItems, maxProperties, format, patternProperties, prefixItems.
Для ответов readOnly остаётся в required: сервер его возвращает. writeOnly пока не исключается нигде — это известное ограничение.
JSON Schema · draft 2020-12

Что в 2020-12 важно знать при валидации

format — аннотация по умолчанию

Валидатор не проверяет date, email, uuid, пока не включена проверка. Для JsonSchema.Net — RequireFormatValidation = true; тест фиксирует это поведение.

$defs вместо definitions

В 2020-12 используется $defs. Старые инструменты, знающие только draft-07, могут его не понимать.

discriminator не переносится

oneOf выбирает вариант по содержимому. Чтобы варианты не пересекались, добавьте каждому поле с enum: [VALUE] (так сделано в samples/complex).

exclusiveMinimum — число

Флаг из OpenAPI 3.0 превращается в число. Старая форма exclusiveMinimum: true в 2020-12 не валидна.

Приоритеты

Что чинить в первую очередь

1. Маскировка

Исправить CS0120 и подключить конвертер. Добавить тест, который проверяет результат ToMaskedJson(), а не текст.

2. Рекурсия в inline-схемах

BuildSchemaNodeFromInlineAsync должен заходить в properties и items. Это закрывает массивы, объекты и часть List<object>.

3. Типы против правил

Согласовать TypeMapper и RuleMapper: Guid/DateTime не должны проверяться как строки.

4. enum

Пропускаются integer enum; inline enum даёт IsInEnum() на строке. RefResolver не переносит EnumValues.

5. Внешние схемы и HTTP

Схемы из внешних файлов не попадают в граф; HTTP-загрузчика нет.

6. Имена DTO и валидаторов

Префиксы и суффиксы применяются не везде одинаково.

Применение

Когда инструмент подходит и когда нет

Подходит

  • Контракт-первый API: спецификация согласуется до кода.
  • Граница сервиса: схема проверяет сырое тело до десериализации.
  • Контрактные тесты: valid_*.json / invalid_*.json — фикстуры, которые не требуют C#.

Пока не подходит

  • Маскировка PII: не работает.
  • Валидаторы с Guid/DateTime/enum и внешними файлами: не собираются или неточны.
  • Полный клиент API: инструмент его не генерирует (для этого Kiota или NSwag).
  • OpenAPI 3.1 с массивами в type.
