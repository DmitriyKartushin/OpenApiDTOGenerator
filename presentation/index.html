Зачем

Какую проблему решает проект

Если писать руками

DTO расходятся с контрактом

15 схем × 8 полей: переименовали middleName в спецификации — забыли в классе, [JsonPropertyName] остался старый, поле «пропало» в проде.

Валидация дублируется

pattern, minLength, maximum уже описаны в OpenAPI — но в коде их надо переписать в RuleFor(...) и держать в синхроне.

PII утекает в логи

Паспорт, ИНН, СНИЛС попадают в структурные логи и трейсы. Нужен безопасный способ сериализации «того же» объекта.

400 приходит слишком поздно

Кривой JSON доходит до бизнес-логики и падает в неожиданном месте, а не на границе приложения с указанием пути поля.

Если генерировать из спецификации

Dto/ C#-классы

Классы и enum'ы с [JsonPropertyName], XML-doc, nullable-аннотациями и наследованием через allOf.

Validators/ FluentValidation

AbstractValidator<T> с правилами из схемы, каскадом SetValidator и условными правилами .When(...).

Masking/ безопасный JSON

[Mask(...)] на полях + ToMaskedJson() на каждом DTO: одни и те же данные, но без PII.

JsonSchema/ схема тела запроса

Самодостаточная JSON Schema (draft 2020-12) на каждую операцию — валидация сырого тела до десериализации.

Идея: спецификация OpenAPI — единственный источник истины. Артефакты не «пишутся один раз», а перегенерируются в CI, поэтому расхождение «контракт ↔ код» становится невозможным по построению.

Почему не пишем на диск из генераторов

Все 147 тестов генераторов сравнивают строки — быстро, без временных каталогов. IO-ошибки живут ровно в одном классе.

Почему IR, а не прямое чтение дерева

Один контракт между парсингом и эмиттерами: генератор можно тестировать на рукописном SchemaNode, вообще без YAML.

Куда добавлять новое

Новый артефакт — новый класс в Generators + 5 строк в executor. CLI и Core при этом не меняются.

6 шагов внутри GenerateCommandExecutor

  1. Читаем файл — File.ReadAllTextAsync. Ошибка → код 2.
  2. Парсим — new YamlDocumentParser().Parse(content) → дерево Dictionary<string, object?>. Ошибка → код 3.
  3. Строим IR — IRBuilder(refResolver).BuildAsync(tree, inputPath) → Dictionary<string, SchemaNode>. Здесь же резолвятся все $ref.
  4. Генерируем — DTO / Validators / Masking / JSON Schema, каждый под своим флагом (ShouldGenerate… в GenerateOptions).
  5. Пишем — WriteFiles(files, Path.Combine(output, "Dto")): Directory.CreateDirectory + File.WriteAllText (UTF-8 без BOM).
  6. Возвращаем код — 0, а FileNotFoundException / FormatException / прочее ловятся в одном try/catch.

Парсинг YAML · 1/3

YamlDotNet RepresentationModel, а не десериализация в POCO

YamlStream.Load(reader) даёт дерево узлов как есть — без схемы, без модели OpenAPI, без потерь:

  • сохраняется стиль скаляра (в кавычках / без) — критично для строковых кодов;
  • неизвестные ключи (x-*, vendor-расширения) не ломают парсинг;
  • JSON проходит тем же путём — JSON является подмножеством YAML, поэтому отдельный JsonDocumentParser не нужен;
  • любой набор ключей можно конвертировать в текст без «полной» модели OpenAPI.
Ограничение: берётся только Documents[0] — multi-document YAML (---) не поддерживается.
YamlDocumentParser.cs
var yamlStream = new YamlStream();
using var reader = new StringReader(rawContent);
yamlStream.Load(reader);

var root = yamlStream.Documents[0].RootNode;
return ConvertNode(root);

// три вида узлов — и всё
node switch
{
    YamlMappingNode  m => ConvertMapping(m),   // → Dictionary
    YamlSequenceNode s => ConvertSequence(s),  // → List
    YamlScalarNode   v => ConvertScalar(v),    // → scalar
    _ => throw new InvalidOperationException(…)
};
Любая ошибка YamlDotNet оборачивается в FormatException("Failed to parse YAML content: …") — CLI превращает её в код 3 и не печатает стек, если не --verbose.

$ref · 2/3

Загрузка и кеш: фабрика вызывается ровно один раз

  • IDocumentLoader — контракт «дай текст по ключу». Реализация LocalFileLoader: проверка «это каталог?», «файла нет?», чтение UTF-8 с CancellationToken.
  • CachedDocument(rawContent, format) — сырой текст + подсказка формата (по расширению). Парсинг выполняется при каждом использовании, кешируется только текст.
  • DocumentCache — ConcurrentDictionary плюс SemaphoreSlim на ключ: быстрый путь без блокировки, затем double-check после захвата. Две параллельные ветки не скачают файл дважды.
  • Нормализация ключа: URI → new Uri(x).ToString().TrimEnd('/'); пути — как есть. Сравнение: OrdinalIgnoreCase на Windows, Ordinal на Linux (регистр в путях значим).
DocumentCache.GetOrAddAsync
if (_store.TryGetValue(key, out var existing))
    return existing;                       // быстро

var sem = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
await sem.WaitAsync(ct);
try
{
    if (_store.TryGetValue(key, out existing))
        return existing;                   // double-check

    var doc = await factory(key);      // загрузка+парсинг
    _store[key] = doc;
    return doc;
}
finally { sem.Release(); }
Один и тот же экземпляр кеша живёт на весь запуск generate: money.yaml, на который ссылаются 5 схем, читается и парсится один раз.
$ref · 3/3

JSON Pointer по RFC 6901 — с человеческими ошибками

  • "/components/schemas/Foo" → токены ["components","schemas","Foo"]; ведущий / отрезается.
  • В объекте — поиск по ключу, в массиве — по индексу (int.TryParse, проверка границ).
  • Скаляр или null дальше не разворачиваются — это ошибка, а не «пусто».
  • Escape: ~1 → /, затем ~0 → ~. Порядок обязателен: иначе ~01 превратится в ~/.
  • Пустая строка и "/" → корень документа (ссылка на весь файл).
В сообщении об ошибке печатаются доступные ключи — отладка спеки занимает секунды: Key 'PersnInfo' not found. Available keys: [PersonInfo, …]
JsonPointerResolver.Navigate
foreach (var rawToken in tokens)
{
    var token = Unescape(rawToken);   // ~1, затем ~0

    switch (current)
    {
        case Dictionary<string, object?> dict:
            if (!dict.TryGetValue(token, out current))
                throw new JsonPointerException(…);
            break;

        case List<object?> list:
            // int.TryParse + проверка 0 <= index < Count
            current = list[index]; break;

        case null: throw … // «нельзя идти в null»
        default:  throw … // «скаляр — не контейнер»
    }
}
Тот же резолвер используется и в RefResolver, и в JsonSchemaGenerator — поведение одинаковое.
Циклы

Рекурсия в спецификации — две разные стратегии

IR детектор + ленивая ссылка

CycleDetector.cs
public void Enter(string key)
{
    if (_visiting.Contains(key))
    {
        var cyclePath = new List<string>(_stack) { key };
        throw new CyclicReferenceException(key, cyclePath);
    }
    _stack.Add(key); _visiting.Add(key);
}
  • List хранит путь от корня, HashSet даёт O(1) проверку.
  • Leave строго LIFO — иначе InvalidOperationException.
  • CycleDetectorScope — RAII: using (detector.Scope(ref)) автоматически вызывает Leave при выходе (в т.ч. при исключении).
  • В IRBuilder исключение перехватывается и превращается в узел { OriginalRef, IsLazyRef = true }.

JSON Schema очередь вместо рекурсии

RegisterDefAsync — цикл безопасен по построению
if (!ctx.DefNames.TryGetValue(refKey, out var defName))
{
    var target = Resolve(tree, pointer);
    defName = ctx.ReserveDefName(BuildDefBaseName(pointer, docKey));
    ctx.DefNames[refKey] = defName;              // регистрируем ДО конвертации
    ctx.Pending.Enqueue(new PendingDef(defName, target, docKey));
}
return $"#/$defs/{defName}";   // ссылка возвращается сразу
Ссылка на саму себя — это просто строка #/$defs/Comment. Тело Comment конвертируется позже, когда очередь дойдёт до него. Никакой бесконечной рекурсии.
Что важно знать про IR-ветку: ленивый узел не получает имя, поэтому рекурсивное свойство сегодня генерируется как List<object> (см. слайд 30). Для JSON Schema та же схема работает корректно — это лучший путь для рекурсивных структур.
IR

SchemaNode — единственный контракт между парсингом и генерацией

Core/Models/SchemaNode.cs (сокращённо)
public sealed record SchemaNode
{
    public string? Name { get; set; }        // ключ components/schemas
    public string? OriginalRef { get; set; }
    public string? Type { get; init; }
    public string? Description { get; init; }

    public IReadOnlyList<PropertyNode> Properties { get; init; }
    public SchemaNode? Items { get; init; }
    public IReadOnlyList<string> EnumValues { get; init; }

    public IReadOnlyList<SchemaNode> AllOf / OneOf / AnyOf { get; init; }
    public string? DiscriminatorPropertyName { get; init; }
    public IReadOnlyDictionary<string, string> DiscriminatorMapping { get; init; }

    public ValidationRules Rules { get; init; }
    public bool IsLazyRef { get; set; }

    // вычисляемые
    public bool IsObject  => Type == "object" || Properties.Count > 0;
    public bool IsArray   => Type == "array";
    public bool IsEnum    => EnumValues.Count > 0;
    public bool IsPrimitive => Type is "string" or "integer" …;
}
PropertyNode + ValidationRules
class PropertyNode {
    string Name;            // как в YAML: lastName
    SchemaNode Schema;      // тип/вложенная схема
    bool IsRequired;        // из required родителя
    string? Description;
}

class ValidationRules {
    int? MinLength, MaxLength, MinItems, MaxItems;
    string? Pattern, Format;
    double? Minimum, Maximum;
    bool ExclusiveMinimum, ExclusiveMaximum,
         UniqueItems, Required, Nullable;
}
record + with — узлы собираются по шагам: сначала Type/Description/Rules, потом with { EnumValues = … }, потом with { Properties = … }. Иммутабельность даёт бесплатный кеш и безопасную параллельность.
Что IR сознательно не хранит: additionalProperties, readOnly, examples, patternProperties. Поэтому JSON Schema идёт мимо IR.
IRBuilder

Как строится граф: 8 шагов на каждую схему

  1. Взять components/schemas — ключи становятся именами схем.
  2. Кеш _builtNodes — повторный вход возвращает готовый узел (защита от повторной сборки).
  3. Войти в CycleDetector.Scope(schemaName) — RAII-стек обхода.
  4. Создать узел: Name, Type, Description, Rules (из ExtractValidationRules).
  5. Enum? — есть enum → заполнить EnumValues и выйти: у enum нет ни свойств, ни вложенности.
  6. Array? — рекурсивно построить Items из items.
  7. Object? — properties → PropertyNode + IsRequired из required родителя.
  8. Полиморфизм — allOf, oneOf (+ discriminator и mapping), anyOf; сохранить узел в кеш.
BuildSchemaNodeAsync — скелет
using (_cycleDetector.Scope(schemaName))
{
    var node = new SchemaNode {
        Name = schemaName,
        Type = ExtractType(schemaDict),
        Description = ExtractDescription(schemaDict),
        Rules = ExtractValidationRules(schemaDict),
    };

    if (ExtractEnum(schemaDict) is { Count: > 0 } values)
        return node with { EnumValues = values };

    if (node.Type == "array")
        node = node with { Items = await … };

    node = node with { Properties = await ExtractProperties(…) };
    node = node with { AllOf = await BuildSchemaList(…) };
    // + OneOf/Discriminator, AnyOf
    _builtNodes[schemaName] = node;
    return node;
}
Где именно теряется информация: BuildSchemaNodeFromInlineAsync (для свойств и элементов allOf) извлекает только Type/Description/Rules/Enum и не рекурсирует в properties и items. Поэтому inline-объект и inline-массив в DTO превращаются в object / List<object>. Полный список — слайд 31.

TypeMapper — nullable поверх базового типа
public string Map(SchemaNode node, bool applyNullable = false)
{
    var baseType = MapCore(node);

    if (applyNullable && node.Rules.Nullable
        && !baseType.EndsWith('?')
        && !baseType.StartsWith("List<"))
        return baseType + "?";

    return baseType;
}
List< исключён намеренно: List<T>? и List<T> в DTO ведут себя почти одинаково, а nullable-аннотация на коллекции только шумит.
Несколько источников «?»: nullable: true в схеме и отсутствие в required (см. DtoGenerator.AppendProperty). Второе правило сильнее: опциональное поле всегда nullable.

  • Имена: NameHelper.ToPascalCase бьёт по _ и -, капитализирует части. document_type → DocumentType.

Про [EnumMember]: атрибут фиксирует исходное значение (NOT_SPECIFIED), но System.Text.Json его не читает — для сериализации строкой нужен JsonStringEnumConverter или свой конвертер. Сейчас enum-поля в DTO почти всегда string (см. слайд 31), так что вопрос отложен, но при «оживлении» enum'ов его придётся решить.

Три решения на каждое свойство

1. Примитивные правила

RuleMapper.Map(prop) — чистый список строк, без знания о классе. Поэтому RuleMapperTests проверяют правила таблицей, без генерации файлов.

2. Каскад SetValidator

Вложенный объект с именем → new XxxValidator(). FluentValidation сам не заходит внутрь объектов, поэтому без этого правила вложенные поля не проверяются.

3. .When по дискриминатору

GetDiscriminatorValue ищет значение, чья схема «похожа» на имя свойства: schemaName.Contains(PascalCase(prop)) или prop.Contains(discriminatorValue).

Честно: это эвристика по именам, а не семантика. Для passport → PassportInfo работает, для произвольных имён — нет. Надёжнее опираться на oneOf + discriminator.mapping в самих схемах вариантов (как в samples/complex).

JSON Schema · 1/6

Зачем схема тела запроса и почему генератор идёт мимо IR

Зачем

  • 400 до десериализации. Тело проверяется как JSON-документ: путь до поля (/applicant/birthDate), а не «string → DateOnly failed».
  • Язык-независимый контракт. Тот же файл читают gateway, тесты, моки, другие сервисы — не только .NET.
  • Строгие вещи, которых нет в DTO: additionalProperties: false, uniqueItems, maxProperties, oneOf.
  • Документ самодостаточен. Один файл = все $defs, без сети и без исходного YAML.

Почему не по SchemaNode

  • В IR нет additionalProperties, readOnly, examples, uniqueItems, maxProperties, patternProperties — а в JSON Schema они обязаны быть.
  • IR склеивает inline-объекты и теряет их структуру, а для валидации нужен каждый уровень.
  • Для схемы нужны все $ref-цепочки, включая внешние файлы и requestBody → components/requestBodies, а не только components/schemas.
Поэтому JsonSchemaGenerator получает documentTree + documentKey и работает с произвольными узлами через Dictionary<string, object?>.
Ключевое различие: DTO/валидаторы отвечают на вопрос «удобно ли работать в C#», JSON Schema — «валиден ли байт-в-байт присланный JSON». Это разные задачи, поэтому и два разных представления.

Алгоритм: от paths до файла на операцию

  1. Обойти paths и для каждого HTTP-метода из EffectiveHttpMethods (по умолчанию post) найти операцию.
  2. Развернуть requestBody — ResolveRefChainAsync идёт по цепочке $ref (например в components/requestBodies), помнит посещённые ключи и падает на цикле.

Почему до десериализации

Схема видит «лишние» поля, неверные типы и нарушения в глубине дерева. Сериализатор бы молча проигнорировал лишнее или упал с общей ошибкой.

Две ловушки

1. format — аннотация. В draft 2020-12 date, email, uuid по умолчанию не проверяются. Нужен RequireFormatValidation = true (есть тест, который это фиксирует).
2. discriminator не переносится. oneOf выбирает вариант по содержимому — чтобы варианты исключали друг друга, добавьте в каждую схему поле-дискриминатор с enum: [VALUE] (так сделано в samples/complex).

Несколько операций: загрузите все файлы один раз на старте и выбирайте по method + path из index.json.

Честный разговор

Что чинить в первую очередь

1. Рекурсия в BuildSchemaNodeFromInlineAsync

Сейчас inline-схема читается «в один уровень». Рекурсивный вызов для properties/items/allOf закрывает сразу четыре строки матрицы: inline-массив, inline-объект, allOf, циклы.

2. EnumValues при резолве $ref

RefResolver.ConvertToSchemaNode копирует только Type и Description. Добавить EnumValues/Rules — и enum'ы начнут работать: Gender, DocumentType, IsInEnum().

3. Согласовать имена DTO и валидаторов

DtoValidatorOptions.ClassSuffix есть, но CLI его не передаёт, а SetValidator вообще игнорирует prefix/suffix. Один общий ClassNameResolver решает проблему.

4. Внешние схемы в IR

Money/Address упоминаются в типах, но не попадают в Dictionary<string, SchemaNode> (он строится только из components/schemas корня). Нужно «дотягивать» внешние схемы в тот же граф и генерировать для них DTO/валидаторы.

5. RemoteHttpLoader

Классификация Remote уже есть; нужна реализация IDocumentLoader поверх HttpClient — и HTTP-$ref заработает во всех четырёх генераторах.

6. Мелочи, которые видит потребитель

required-модификатор или инициализаторы (CS8618); JsonStringEnumConverter для enum'ов; не генерировать пустые валидаторы; писать [Mask] только на string.

Хорошая новость: всё это — точечные правки в Core/Generators, тесты на каждый случай уже есть или добавляются одним файлом.
Кейсы

Где проект даёт выигрыш сразу

1. Контракт-первый backend

Команда сначала согласует openapi.yaml, потом генерирует DTO и валидаторы в CI. Расхождение «спека ↔ код» ловится на сборке, а не на ревью. Подходит: новые сервисы, команды с API-first процессом.

2. PII в логах и трейсах (152-ФЗ)

Один и тот же DTO: JsonSerializer.Serialize — для отправки, ToMaskedJson() — для логов. Маскировка описана декларативно в YAML, а не размазана по коду логирования. Подходит: финтех, HR, медицина, любые персональные данные.

3. Граница сервиса / gateway / BFF

JSON Schema проверяет сырое тело до десериализации: лишние поля (additionalProperties: false), uniqueItems, точный путь ошибки. Один файл — для .NET, Node, Go и тестов. Подходит: публичные API, партнёрские интеграции.

4. Тестовые данные и моки

Схема — источник валидных/невалидных фикстур. В проекте это уже работает: valid_*.json / invalid_*.json гоняются через JsonSchema.Net. Тот же набор — для контрактных тестов потребителей.

5. Контрактные тесты в CI

generate идемпотентен, код выхода говорит о типе ошибки. Добавили invalid_*.json — получили регрессионный тест на схему без единой строки C#-кода.

6. Миграция legacy

Есть только swagger.yaml от старой системы — генерируем DTO и валидаторы, получаем типизированный контракт и одинаковые сообщения об ошибках.

Когда не подходит: нужен полный клиент API (Kiota/NSwag), OpenAPI 3.1 с type: [..] массивами, code-first без спеки, или требуется DI-регистрация валидаторов «из коробки» — этого здесь нет.

Шпаргалка

Вопросы, которые задают чаще всего

«Почему не NSwag / Kiota?»

Они генерят клиентов и модели, но не дают JSON Schema тела запроса и маскировку PII, а валидаторы получаются «в стиле» конкретного инструмента. Здесь — узкая задача с полным контролем над выводом.

«Что будет, если в YAML опечатка?»

FormatException → код 3, сообщение без стека (стек — с -v). Неизвестный ключ (x-foo, foo) не ломает парсинг: дерево универсальное.

«Как понять, почему поле стало object?»

Смотреть BuildSchemaNodeFromInlineAsync: он не рекурсирует в properties/items. Проверить можно, распечатав IR в --verbose или в тесте на IRBuilder.

«Генерация детерминирована?»

Да для JSON Schema (SortedDictionary для $defs, фиксированный порядок свойств из словаря). DTO/валидаторы идут в порядке components/schemas.

«Где валидируется то, чего нет в схеме?»

Нигде — и это осознанно. Бизнес-правила (контрольные суммы ИНН, возраст) в OpenAPI не выразить: для этого есть ручные валидаторы поверх сгенерированных.

«Можно ли использовать только JSON Schema?»

Да: --json-schema-only. Это самый зрелый путь — 52 интеграционных теста, включая реальную валидацию тел запросов.

«Почему ToMaskedJson, а не настройка логгера?»

Правила живут рядом с данными, а не в конфиге логгера, и переживают рефакторинг: переименовали поле — правило в YAML обновили один раз, атрибут перегенерировался.

«Сколько стоит добавить новый проект в решение?»

Core — единственная зависимость от YamlDotNet. Всё остальное — BCL. Рантайм-зависимостей у сгенерированного кода нет, кроме FluentValidation.
